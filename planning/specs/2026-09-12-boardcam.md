# BoardCam — clock-triggered OTB game recorder (photos → PGN)

## Problem
Isaac and a friend play over-the-board rapid (10+5) with a phone chess clock
and want to analyse every game afterwards, but neither remembers the full move
sequence, so recreating the game in an engine is slow and partial. Photographing
key positions by hand interrupts play, and single-photo LLM transcription of
this abstract-piece set has proven unreliable (flipped colours, confused piece
types, wrong squares). What is needed is a zero-workload recorder: a second
phone on the existing stand photographs the board every time the clock is
pressed, and the game comes out the other end as a correct PGN.

## Solution
Two phones open one web app served from Isaac's Mac through an ngrok tunnel
(HTTPS is mandatory for mobile camera access). The **clock phone** runs the
chess clock; every press is an event over WebSocket. The **camera phone** sits on
the stand, holds a live camera stream, and on each press grabs a short burst of
frames and uploads them. Frame 0 (start position) is captured automatically
before the first press.

The engine never classifies piece types from pixels. Because the start position
is known and every ply is photographed, the position is *tracked*: each new
frame is compared to the previous one, the pattern of changed squares plus a
per-square occupancy cue is scored against every legal move (also "no move" and
two-move pairs, to survive a missed or double press), and a beam search over
the whole game picks the globally most likely sequence — later frames resolve
earlier ambiguities. Board corners, square colours and which side is white are
detected automatically per game (camera position, lighting, board and pieces
may all change between games). The camera sits low and to the side (~30°
elevation), so pieces hide the squares behind them; the engine therefore reads
moves from where change blobs *touch the board* (piece footprints projected
through the calibration), and analyses only the board area plus a strip above
its far edge, so hands, players and captured pieces beside the board are
invisible to it. Low-confidence plies are resolved automatically
by a vision-LLM call (Sonnet 5, escalate to Opus 5) that chooses among the
engine's candidates. Output: PGN with `%clk` times, one-tap lichess import, and
a review page where a wrong ply can be corrected; corrections re-run the tracker
from that ply and become labelled data for a tuning script that refits the
engine's scoring parameters. The engine is built and gated entirely on a
synthetic renderer that randomises camera pose, lighting, board/piece styles,
orientation, hands and jitter; the first real games are the final phase.

  the corpus-size difference.
- [F] `engine.evaluate data/synth/hard` / `nightmare` → not run; the primary gate
  fails, so these would only have measured the same shortfall twice.
- [x] runtime **0.27 s/frame** at beam width 30, inside the 0.5 s budget.

**Where it actually stands.** Per-frame, scoring every legal move from the true
board, the engine ranks the true move first on **98 % of `clean` frames and 88 %
of `shallow` frames**, with the truth in the top three 97.8 % of the time. The
whole gap between that and the numbers above is the search failing to hold on to
a game the model already prefers — measured directly: the true sequence scores
**60–180 nats better in total** than the sequence the beam returns, while never
falling more than **4.4–6.7 nats** behind at any prefix. Widening the beam does
not fix it (30, 80 and 200 give identical accuracy), so the field has to be made
smaller rather than the search bigger. Index-wise scoring also makes this look
worse than it is: one wrong ply at move 16 scores zero for every ply after it,
even where the tracker is still following the game correctly from its own board.

**What to try next, in order** (from the Fable diagnosis, which the measurements
above bear out):
1. Re-tune `q_hit`, `nu`, `prior_null` and `tau` *against the beam*, not against
   per-frame top-1. Every parameter in `params.json` was fitted on per-frame
   accuracy, and per-frame accuracy is not the thing that is failing. `tau`
   especially: the flag threshold was calibrated when margins were ~3 nats and
   they are now ~40, which is why recall collapsed while flags per game fell.
2. Estimate the per-square piece placement offset online. The renderer offsets
   every square by up to ±0.25 squares and keeps it fixed for the game, real
   players do the same, and the engine currently assumes dead centre — this is
   what the five failing tracker tests are measuring.
3. Only then revisit the occupancy term, whose weight may have been fighting the
   mis-scaled mass channel rather than the data.

## Notes

### A. Protocol (Phase 1 writes the authoritative `docs/PROTOCOL.md`; this is the design)
- Room: camera phone creates the game (`POST /games`) and shows a 4-char code + QR; clock phone joins with the code. Both connect to `WS /ws/{room}?role=`. Rejoin with the same role replaces the stale socket. Heartbeat every 10 s.
- Clock → server events (persisted, forwarded): `clock.config{initial_ms, increment_ms, white_name, black_name}`, `clock.start{t}` (white's first press, seq 1), `clock.press{seq, side, white_ms, black_ms, t}`, `clock.pause`, `clock.resume`, `clock.flag{side}`, `clock.stop{result}`, `clock.reset`.
- Server → camera: `capture{seq}` on start/press/flag/stop (stop captures one final frame in case the last move was never pressed). Camera uploads `POST /games/{id}/frames/{seq}/{k}` for k in 0..2 (burst at +0/+400/+900 ms; cut short if a new `capture` arrives). Pre-start: camera uploads frame 0 every 2 s until `clock.start`.
- Server → clock: `frame.ok{seq, k}`, `calibration{ok, score, warning}`, `analysis.ready{pgn, lichess_url, flagged}`.
- Layout: `data/games/<id>/{events.jsonl, frames/<seq>_<k>.jpg, calibration.json, analysis.json, game.pgn, labels.json}`.
- Seq n corresponds to ply n in the normal case; the tracker never assumes it (0/1/2 plies per frame).

### B. Calibration method (Phase 2)
1. Downscale to 1024 long edge, grey, CLAHE, Canny, `HoughLinesP`. Cluster lines by angle into two families (the board's two edge directions; they need not be perpendicular in the image).
2. In each family, find groups of ≥ 7 roughly evenly spaced lines (a perspective-consistent progression) — that is the grid. Take the outermost lines of each group; intersect → 4 corner candidates. Sub-pixel refine with `cornerSubPix`.
3. Validate: rectify to 512², compute the checker score = normalised correlation between the rectified ranks 3–6 (empty at frame 0) and the ideal ± checker pattern for the two possible colour phases; take the better phase; require score ≥ `checker_min`. Also require the two occupied bands (ranks 1–2 and 7–8) to differ from their squares' background far more than ranks 3–6 do.
4. Fallbacks in order: next-best line group; vision-LLM asked for approximate normalised corner coordinates then local line search around them (Phase 4 wires the LLM; Phase 2 leaves the hook); manual corner drag on the camera phone.
5. Camera side = board edge whose image-space length is largest (nearest the camera). Square colours from step 3's phase. White side = occupied band whose piece pixels are brighter (piece pixels = pixels far from the square's own empty-colour model; compare medians). Handedness: with white side and square colours known, choose the unique rotation where white's right-hand corner square is light.
6. Per-frame drift: re-run steps 1–3 restricted to a ±20 px band around the previous corners; accept if the checker score holds, else keep the prior corners and emit `drift`.

### C. Emission model (Phase 3 — implement as written, then tune)
Geometry that drives everything here: the camera is ~30° above the board plane
and to the side. A piece of height h standing on square S projects a silhouette
that extends `h / tan(elev)` (≈ 1.7 h at 30°) *away from the camera* beyond S in
the rectified board plane — up to three squares for a king. So the pixels of a
square mostly show whatever stands in front of it, and per-square patch
statistics are unreliable. What *is* reliable is where a silhouette touches the
board: the lowest image-space edge of a piece's change region is its base, and
projecting that through the calibration lands on the piece's true square.

**Mask.** Only pixels inside the board quadrilateral plus a strip above its far
edge (height `max_piece_h · f / tan(elev)`, estimated from the calibration with
an approximate focal length = image width) are analysed. Hands at rest, players,
the clock phone and captured pieces beside the board are outside the mask.

**Change blobs.** `R_t` is the masked raw frame (median of surviving burst
candidates) photometrically normalised to `R_{t−1}` inside the mask. Change mask
`M = |grey(R_t) − grey(R_{t−1})| > θ`, morphological open then close (3 px),
connected components, drop blobs with area < `min_area`. Blobs cut by the
mask boundary at the *far* strip (torso/background motion) with no pixels
reaching the board interior are discarded.

**Footprints.** For each blob b: footprint pixels = the lowest 20 % of b along
the image-space vertical (toward the camera side); project them through `H⁻¹`
to board coordinates; `mass_b(s)` = fraction of footprint pixels landing in
square s, then spread **ray-consistently**: a partially hidden piece's visible
bottom lies *beyond* its true square along the camera ray, so `mass_b` is also
credited, with geometric decay `ρ^k` (ρ = 0.4), to the k-th square nearer the
camera along the projection direction. `z_s = Σ_b mass_b(s)`; `A_b` = blob
area, capped at `cap_area` so one hand or torso cannot dominate.

**Occupancy evidence** (secondary). Square s is *observable* at frame t iff
the tracked state has no piece on any of the squares within `ceil(h_type /
(w·tan(elev)))` squares directly in front of s toward the camera. For
observable squares only: empty-colour model `(μ_s, Σ_s)` in Lab over the near
strip of s (the 30 % of the square nearest the camera, which its own piece's
base covers), bootstrapped at frame 0 from observable empty squares of the same
colour and updated by exponential averaging while s is tracked as empty;
`o_s` = Mahalanobis distance; `p(occupied | o_s) = σ(a·(o_s − b))`.

**Candidates** for the transition t−1 → t from board B: `∅` (nothing changed),
each legal move m, and pairs (m₁, m₂) with m₂ legal after m₁ — pairs are only
generated when the best single candidate's margin over `∅` and the runner-up is
below `pair_trigger`. Promotions are 4 candidates each.

**Changed set** `C(c)`: squares whose content differs between B and B·c
(from, to, rook squares for castling, captured pawn for e.p.).

**Log-likelihood.**
```
L(c) = Σ_{s∈C(c)}  log( ε_hit + (1−ε_hit) · min(1, z_s / m_hit) )        # each changed square must be hit by footprint mass
     − λ_unexpl · Σ_b  min(A_b, cap_area) · (1 − Σ_{s∈C(c)} mass_b(s))   # blob mass not explained by the candidate
     + Σ_{s observable} log p(occ_s = occupied_after(B·c, s) | o_s)      # secondary, only where the view is clear
     + log prior(c)
```
with `prior(∅) = 0.02`, `prior(m) = 0.95 / |legal|`, `prior(pair) = 0.03 /
|pairs|`. Initial params: `θ = 25 (grey levels), min_area = 40 px, m_hit = 0.15,
ε_hit = 0.03, λ_unexpl = 2.5 (per 1000 px), cap_area = 4000 px, ρ = 0.4,
a = 2, b = 3, pair_trigger = 2.0 nats, divergence_floor = −60, τ = 3.0 nats`.
All live in `engine/params.json`; `scripts/tune.py` refits them. A move whose
from- and to-squares are both fully hidden behind taller pieces (possible at 30°)
yields little footprint mass; that is exactly the case the beam, the occupancy
term on the *revealed* squares, and the Phase 4 LLM fallback exist for.

**Beam.** Width 5 over full game paths. Per-ply posterior margin = log-sum-exp difference between paths agreeing and disagreeing with the best path at that ply. Margin < τ → `low_margin` flag (→ LLM in Phase 4). Best `L` < `divergence_floor` → `unexplained`. Promotion variants that later moves cannot distinguish → `promotion_unknown` (default queen, LLM asked). Frame 1 must change squares on white's side; if instead black's side changed, flip `white_side` and restart — the second orientation check.

**Why this works without piece recognition.** Identity is carried by the tracked state; the image only has to answer "where did change touch the board" and, where the view is clear, "is this square occupied" — both near-binary signals with a fixed camera. Legal-move constraints turn a noisy 64-vector into a choice among ~30 discrete hypotheses, and the beam lets later frames vote on earlier ones.

### D. Decisions taken in this spec (from Isaac's answers, 2026-09-12)
- Hosting: Mac + ngrok (static free domain) — the Mac must be at the venue or reachable. Cloudflare Tunnel is the documented alternative if the ngrok interstitial becomes annoying (needs a domain).
- Fully automatic first; review page is for *correcting* not confirming, and every correction is training data for `tune.py`. "Training" here is refitting the scoring parameters and growing the labelled corpus; a learned piece classifier is deliberately out of scope.
- Synthetic-first because camera position, lighting, board, pieces and white's side all vary between games — so per-game auto-calibration is a hard requirement, not a nicety.
- Camera geometry confirmed 2026-09-12: ~2 ft above and 3–4 ft to the side (~30° elevation), players' hands, bodies and captured pieces in frame. The `shallow` renderer profile reproduces this and is the primary gate; the emission model is footprint-based for that reason.
- Stack: Python 3.13 venv (opencv wheels; 3.14 not guaranteed), FastAPI, python-chess, OpenCV headless, vanilla JS PWA (no build step), kaczor-design tokens.
- Out of scope for V1: takebacks, adjustments outside a move (j'adoube) — handled by correction; chess.com import (no API; copy PGN); multi-game sessions without reset; Bluetooth pairing (Web Bluetooth is absent on iOS Safari).

### E. Risks
- Synthetic-to-real gap in calibration (real boards have coordinates, borders, glare). Mitigation: Phase 6 tuning + manual-corner fallback that never blocks a game.
- Hand in every burst candidate during fast time-trouble play. Mitigation: bursts are cheap; the tracker tolerates a bad frame by scoring it as `∅`/`unexplained` and catching up with a pair on the next frame.
- Shallow camera (~30°): pieces hide up to three squares behind them, and a moved piece can be almost fully hidden. Mitigation: footprint-based scoring with ray-consistent spread, occupancy only on observable squares, `shallow` is the primary synthetic gate, LLM fallback; guidance to mount the phone as high as the stand allows because every 10° of elevation shrinks occlusion.
- Players, hands and captured pieces moving in frame. Mitigation: hard mask (board + far strip), blob-mass cap, far-strip blobs that never reach the board interior are discarded, burst filtering; the renderer's `shallow`/`hard` profiles include all of this noise so the gate measures it.
- iOS Safari pausing the camera stream when the screen dims. Mitigation: wake lock; documented "keep the camera page in the foreground".

### 2026-09-12 — Phase 3 execution deviations

**Notes §C was implemented as written, measured, and then replaced.** The
footprint model — change blob, lowest pixels, project through `H⁻¹`, spread
ray-consistently — reached **32.6 % of plies correct on `clean`**, the easiest
corpus, against a 99.5 % gate. The failure is structural, not a tuning problem,
and one frame shows it: on a kingside castle the true candidate did not reach
the top six, because at a shallow angle the pieces on a rank line up along the
camera ray and therefore share image *columns*. The bottom contour of a change
blob only ever reveals the nearest piece's base, so the rook at h1 contributed
no footprint mass at all. Inferring squares backwards from the change region
cannot work at this geometry, with or without the ray-consistent spread §C adds
to paper over it.

**What replaced it: a forward model.** Because the position is *tracked*, the
engine knows the type of the piece on every square, hence its height (0.85–1.75
squares) and base radius. So each candidate **predicts** an image region — the
projected prisms of the pieces it removes and the pieces it adds — and the score
asks how well that prediction matches. This needs a metric camera, which §C did
not call for; `engine/camera.py` recovers one from the board homography alone
(the two image-of-the-absolute-conic constraints give the focal length, and the
rest follows), and it is accurate to **0.06° of elevation** against `truth.json`.
Predicting rather than inferring is what makes the low camera survivable: a
piece that moves out from behind a king produces change only where the king was
not, and a piece that moves *behind* a king produces almost none. Both fall out
of projecting two silhouettes and letting the nearer occlude the further.

**Three model errors found by looking at single frames, each worth knowing:**
1. *Captures were being cancelled as non-events.* The rule "where a piece's old
   and new silhouettes overlap, nothing changes" is right for a piece that
   travels and wrong for one that is replaced — a dark bishop landing on a light
   pawn changes every pixel. Departures are now matched to arrivals of the same
   colour and type, nearest first, and only a matched pair cancels. Clean
   per-frame accuracy 90 % → 96 %.
2. *The occupancy term summed over observable squares.* Every term is a
   log-probability and so never positive, which means a position that hides more
   of the board scored higher for free — and the beam, given ninety frames to
   compound that, invents a position with more occlusion in it. Now averaged.
   The term still measured negative value afterwards and is switched off
   (`occ_weight: 0`); the machinery stays for `tune.py` to revisit.
3. *The analysis mask was the convex hull of the board and its raised corners.*
   That hull sweeps wide wedges past the two side edges, which at 25–40° is
   exactly where the players' forearms rest. It is now the union of the 64
   per-square prisms, which is the region a piece on the board can actually
   occupy.

**Two detector bugs, both found by measurement rather than by a test:**
- *The focal-length solve divided by a near-zero.* Each of the two conic
  constraints goes singular on its own set of camera poses, and averaging their
  closed-form solutions let the singular one poison the answer (one game: 933 px
  against a true 1233 px, elevation out by 8°). Replaced with a scan of the
  residual both constraints are trying to zero. Mean elevation error over the
  corpus fell from 0.22° to **0.06°**.
- *Hand detection fired on every frame of every game, including `clean`, which
  has no hands.* A wooden board and light pieces sit in the same chroma range as
  skin, so an absolute threshold flags everything and the filter stops
  filtering. The test is now relative: a candidate is dropped when it has
  markedly more of that colour than its siblings from the same burst.

**The escape hatch was used, once, as the spec allows.** After two honest
attempts the gate still failed, so one `general-purpose` agent on `fable` was
given the metrics, `engine/emission.py` and Notes §C, and asked for a diagnosis
and a revised scoring rule only. Its diagnosis matched the measurements and
identified the thing I had not: the saturating coverage term
`log(ε + (1−ε)·min(1, cov/m_hit))` returns exactly 0 once coverage passes
`m_hit`, and the *measured* coverage of a true silhouette on `shallow` is
0.25–0.45 — sitting right at the knee, where the term has already stopped
discriminating. Alongside it, the two mass penalties were linear in raw pixel
area over an arbitrary `/1000`, worth only ~0.5–3 nats of separation, which is
exactly the 4.4–6.7 nat crowding measured at the frame where the search died.

All three terms are now one per-cell log-likelihood ratio: a cell changes with
probability `q` if some silhouette of the candidate predicts it and `q0`
otherwise, `q0` estimated **per frame** from the ambient change rate so a frame
with a hand in it and a quiet frame are not held to one constant, and the sum
tempered by `nu` because sixteen pixels that morphological closing has made into
one blob are not sixteen independent trials. Background mass now cancels between
candidates instead of being charged to all of them, and coverage keeps paying
out all the way to 1 instead of stopping at 0.25.

**The decisive diagnostic, and what it ruled out.** Scoring the *true* move
sequence forward and comparing it with the beam's running leader showed the
model prefers the true game by **60–180 nats overall**, while the true path is
never more than **4.4–6.7 nats** behind at any prefix — and is still evicted
from a beam of width 30. Beam width was then measured directly: **30, 80 and 200
all give identical accuracy** on the failing game. Widening the search is
therefore not the answer and was not pursued; the field had to be made smaller
by sharpening the per-frame likelihood, which is what the rewrite above does.
Two search bugs were fixed along the way: each parent contributed up to
`beam_width` children, so the leader's variants filled every slot and evicted
every rival reading of an earlier ply (now `children_per_path`), and one frame
could punish a path without limit (now `score_clip`).

**Promotions are unresolvable by this engine, by construction.** A rook and a
queen differ by a quarter of a square in height and nothing else the camera can
see, and on the frame that matters the promotion square was 65 % occluded, so
all four variants scored within 0.8 nats. A prior that promotions are queens now
breaks the tie — not because the engine can see it, but because that is how
people play — and **every** promotion is flagged `promotion_unknown` for Phase
4. This matters more than one ply: picking the wrong piece leaves it the wrong
*height* for the rest of the game, and under index-wise scoring one
underpromotion costs 45 plies.

**Speed.** A profile showed 40 % of the time in `board.copy()` + two
`piece_map()` builds per candidate, and most of the rest in `np.unique` and
friends sorting 300-element arrays. Move deltas are now worked out analytically
from the move (verified against the push-and-diff reference on 11 871 moves and
6 246 pairs), and the set algebra uses generation-stamped scratch buffers. **4×
faster**: 0.64 → 0.16 s/frame at width 10.

**Extra files beyond the spec's list.** `engine/camera.py` (the metric camera,
needed by the forward model and reusable by Phase 4's prompt) and
`server/analysis.py` (the live calibration and tracking runner, kept out of
`app.py` because it is all threaded work).

**Phase 3's gate was overridden by Isaac, deliberately.** Told that the gate had
failed and what was failing, he chose to carry on to Phase 4 rather than spend
another session on the tracker. Phase 4 is therefore being built against an
engine that gets 74.6 % of plies on `shallow`, so two things follow and should
not come as a surprise when they do:

- **Phase 4's accuracy gate will fail too.** It asks for ≥ 99.5 % of plies with
  the LLM on, which is not reachable from 74.6 % without. Its *plumbing* gates —
  the mocked tests, the schema, the escalation and call-cap behaviour, the live
  smoke test — are independent of the tracker's accuracy and are the ones worth
  taking seriously this phase.
- **The LLM will be shown the wrong plies.** It only ever sees flagged plies, and

  Raising recall is a `tau` question in Phase 3, not something `vision_llm.py`

### 2026-09-12 — Phase 4 execution deviations

**Beam integration scoped to one call per frame, not one per beam path.** The
spec's "adds `log(p_llm)` to the matching candidate at that ply" is agnostic
about whose candidates get asked. Asking every path in the beam would multiply
calls by the beam width for no real gain — at a decisive frame nearly every
surviving path shares the same current board, so their candidate sets
coincide — so `_step` asks only about `self.beam[0]`'s (the current leader's)
top candidates, and applies the resulting bonus to *any* path in the beam whose
candidate at that frame shares the exact same move signature (matched by UCI,
not by path identity). This keeps the design inside the 10-calls-per-game
budget by construction rather than by luck.

**No separate "open question" function for `unexplained` frames.** The spec
described a second, differently-worded call for the unexplained case. Instead
`_consult_llm` takes the same `scored` list and widens it (top 12 instead of
top 6) when the frame is `unexplained`, since `_score_board` already expands to
pair candidates once the single-move margin is small — which is exactly the
`unexplained` condition most of the time. One prompt, one schema, one code
path; the candidate list itself carries the "or two moves" case.

**Caching keyed on `seq` alone, not `(seq, board_fen)`.** Different beam paths
scored at the same frame can, in principle, disagree about the board and thus
about what a given label means. This was scoped out deliberately: the
consult only ever happens against `self.beam[0]`'s board (see above), so one
key per frame is unambiguous for the case that is actually built. A future
`constrain()`-driven correction that revisits an already-resolved frame with a
genuinely different board would get a stale cached answer; this is flagged
here rather than fixed, since it cannot happen with the current one-path-only
design and fixing it now would be solving a problem that does not exist yet.

**Live smoke test result: gate not met, and the diagnosis says why re-running
larger won't help.** `pytest tests/test_vision.py -m live` made 3 real calls
against `data/synth/hard/000-feature-castle-promote-ep` — every answer was
schema-valid (the plumbing gate), but only 1 of 3 matched truth against the
gate's ≥ 2/3. Saved the raw images sent for inspection (`/tmp/vision_debug/`,
not committed) and found:

1. A bishop-vs-knight-to-h6 ambiguity was answered as a pawn push instead of

   cone/cylinder shape, differing only by height (bishop ≈ 1.2× pawn, per
   Notes §A), so two adjacent height classes are genuinely indistinguishable
   in the rendered image. No prompt fixes an image with no signal in it.
2. A rook move in a cluttered, hand-occluded midgame frame was answered "no
   move happened" — exactly the scene noise the `hard` profile exists to
   contain (Notes §E); plausibly a human would miss it too from the same crop.
3. The underpromotion question — the one case this module exists for, since
   the engine itself cannot ever resolve it — was answered *correctly* after
   escalating to Opus on low confidence.

Given (1) and (2) are properties of the synthetic renderer and the `hard`
profile's deliberate difficulty, not of `vision_llm.py`, a full-corpus run
would very likely reproduce the same ≈ per-frame miss rate at ~$10–25 of real
spend without adding information — the smoke test already identifies the
failure mode and confirms the plumbing (schema, escalation, cost) works.
Presented this to Isaac with the diagnosis and the estimated cost; he chose to
skip the full-corpus `engine.evaluate` runs and move on rather than spend
against a predicted outcome, the same call he made overriding Phase 3's gate.

synthetic run — is the point this module's piece-identity value can actually
be measured; the location/occlusion failure mode (case 2) is exactly what
Phase 6's field test and the review page's correction loop exist to catch.
